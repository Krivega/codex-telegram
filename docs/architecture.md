# Архитектура

Одна локальная программа, одна база SQLite, один личный Telegram-бот. Код организован по задачам: `config`, `setup`, `codex`, `telegram`, `storage`, `bridge`, `artifacts`.

`Bridge` выполняет сценарии. `CodexPort` и `TelegramPort` отделяют их от протоколов и позволяют проверять маршрутизацию без сетевых запросов. `Store` отвечает за постоянное состояние и транзакции. Дополнительные процессы, брокеры сообщений и отдельная служба базы данных не нужны.

## Codex

Подключение: дочерний `codex app-server proxy --sock PATH`, без оболочки и интерполяции пользовательского текста в командную строку. Инициализация JSON-RPC выполняется один раз на соединение. Служба использует `thread/list`, `thread/read`, `thread/turns/list`, `thread/queue/add`, `thread/queue/list`, `thread/queue/start`.

При отправке проверяются доступность задачи и `canAcceptDirectInput`. `thread/start`, `thread/fork` и `thread/resume` не вызываются. Исходный клиент сохраняет владение задачей, разрешениями и инструментами. Служба не обрабатывает системные запросы разрешений положительным ответом.

Первая версия опрашивает сохранённую историю. Это позволяет восстанавливать завершения после отключений без подписки, которая могла бы потребовать возобновления чужой задачи. Для неактивных задач неизменившаяся ревизия не перечитывается. События сервера можно добавить после подтверждения общего подключения; контрольное чтение истории всё равно останется. В больших историях текущий полный обход страниц может требовать оптимизации.

Чтение старого формата истории допускается только при ответе `-32601` на `thread/turns/list`. Остальные ошибки не маскируются. Методы очереди экспериментальные, поэтому обновления Codex требуют проверки совместимости.

## Идентичность и доставка

Адрес ответа: `(telegram.chatId, telegram.messageId) -> (threadId, turnId)`. Идентичность компьютера и бота закреплена за базой. Каждая часть длинного сообщения и каждый документ получают собственную привязку. Название задачи для маршрутизации не используется.

Входящий `update_id` уникален в таблице входящих. Его сохранение и перемещение смещения Telegram выполняются одной транзакцией. Поручение получает постоянный `clientUserMessageId`. После потери подтверждения служба ищет этот идентификатор в очереди и `userMessage.clientId` истории; отсутствие записи не считается доказательством отказа.

Перед сетевой отправкой сохраняется промежуточное состояние. После аварийного завершения оно становится неопределённым. Telegram не даёт клиентского ключа однократной отправки: при потере ответа одновременно гарантировать отсутствие повторов и обязательную доставку нельзя. Выбрана остановка автоматического повтора неопределённой отправки с ручной проверкой.

Подтверждённый итог и предназначенные ему сообщения записываются транзакционно вместе с отметкой обработанного выполнения. Автоматическое исполнение системных разрешений отсутствует.

## Вложения

Список вложений принадлежит конкретному поручению. Проверяются относительные пути, выход за пределы каталога, символические и жёсткие ссылки на недопустимые файлы, формат, размер и SHA-256. Перед отправкой файл перечитывается и проверяется повторно. Только явный список результатов приводит к отправке.

Само создание файла выполняет Codex. Его инструменты и права должны позволять работать с каталогом результатов. Проверка формата не является содержательной или визуальной приёмкой документа.

## Настройки и обратная связь

Пошаговая настройка использует скрытый ввод токена и одноразовую привязку владельца. Конфигурация проверяется целиком до сохранения. Настройки и секреты пишутся через временный файл и переименование. Блокировка исключает одновременный запуск настройки и службы в одном каталоге.

`/feedback` сохраняет замечания локально. При выпуске новой версии разработчик просматривает замечания и ошибки доставки, дополняет проверяемые правила, записывает удачные сценарии и повторяет проверку совместимости. Автоматическая отправка замечаний разработчикам не выполняется.
