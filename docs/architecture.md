# Архитектура

Один узел принимает Telegram, несколько независимых служб работают с локальным Codex. Каждая роль имеет свой каталог состояния и SQLite. Отдельные брокеры сообщений и сервер базы данных не требуются. Node.js предоставляет HTTP, TLS и криптографию.

## Компоненты

- `Coordinator` принимает сообщения владельца, хранит адреса ответов и распределяет поручения по компьютерам.
- `HubServer` проверяет ключи и принимает состояние, итоги и вложения компьютеров. `HubStore` хранит подключения, выданные коды и ревизии подтверждений.
- `AgentLink` синхронизирует локальную очередь с узлом. `AgentStore` сохраняет поручения до исполнения и отчёты до подтверждения узлом.
- `CodexWorker` выполняет только локальные сценарии: очередь исходной задачи, наблюдение завершений и сбор объявленных файлов.
- `DeliverySender` проверяет зарегистрированные файлы и отправляет их через `TelegramPort`.
- `Bridge` сохраняет режим версии 1, соединяя тот же `CodexWorker` с локальным получением Telegram. Логика исполнения и доставки между режимами не дублируется.

Протоколы Codex и Telegram отделены интерфейсами `CodexPort` и `TelegramPort`. Сетевой протокол принадлежит этому проекту и имеет версию в пути `/v1/`. Конфигурации сетевых ролей имеют версию 2; старые конфигурации версии 1 поддерживаются без преобразования базы.

## Идентичность и доверие

Маршрут: `(telegram.chatId, telegram.messageId) -> (hostId, threadId, turnId?)`. Привязка сохраняется для каждой части текста, документа и принятого поручения владельца. Заголовок задачи не участвует в выборе адресата. Одинаковые идентификаторы задач и выполнений на разных компьютерах различаются через `hostId`.

Узел имеет собственный `id`. Компьютер привязан к `(hubId, hostId, chatId)`, поэтому смена сетевого адреса узла не меняет адреса задач. Смена идентичности в уже созданной базе отклоняется. Один ключ и каталог состояния предназначены для одной работающей службы; активное дублирование такой установки не поддерживается.

Токен Telegram хранится только на узле. Компьютер создаёт 256-битный случайный ключ и передаёт его с 256-битным одноразовым кодом. Узел хранит только SHA-256 ключей и кодов. Код живёт пять минут; после первого применения принимает повтор лишь с тем же ключом, чтобы восстановиться при потере ответа. Повтор использованного кода с другим ключом и повтор после отзыва запрещены. Выдача кодов и отзыв доступны через локальную командную строку узла.

Компьютеры одного владельца доверены для отправки результатов собственных задач. Ключ компьютера не даёт доступа к поручениям другого компьютера. Узел определяет `hostId` по ключу и адрес Telegram по своей конфигурации; присланные данные не могут выбирать получателя. Ответ на поручение и каждое вложение дополнительно проверяются по исходному поручению владельца. Спонтанный текстовый итог может относиться к любой локальной задаче, разрешённой настройками компьютера.

Удалённое соединение требует HTTPS; HTTP допускается только через локальный адрес. Возможны встроенный TLS, обратный прокси или SSH-туннель. Клиент проверяет сертификат штатными средствами Node.js и запрещает перенаправления. Секреты не включаются в диагностику. Это не сквозное шифрование: тексты и файлы доступны единому узлу и Telegram.

## Сетевые операции

| Адрес | Назначение и гарантия повтора |
| --- | --- |
| `POST /v1/pair` | Привязка; тот же код и ключ возвращают ту же регистрацию до истечения кода |
| `POST /v1/check` | Проверка доступа без изменения задач; возвращает `hubId`, `hostId`, имя |
| `POST /v1/sync` | Состояние Codex, список задач, отчёты; возвращает только ещё не подтверждённые поручения этого компьютера |
| `POST /v1/events` | Текстовый результат с постоянным ключом; повтор не создаёт вторую доставку |
| `POST /v1/files` | Двоичные байты и ограниченный заголовок описания; проверка поручения, размера, формата и SHA-256 |

Ответы имеют ограниченный размер, запросы JSON — до 2 МиБ. В одном обмене допускаются до 1000 задач и 200 отчётов, выдаётся до 100 поручений. Число и размер файлов ограничивает узел. Проверка ключа выполняется до чтения тела и повторяется после длительного приёма файла. Попытки привязки ограничены 30 запросами в минуту на процесс узла.

Постоянный ключ события дополнен идентификатором компьютера. Узел сохраняет отпечаток содержимого: повтор ключа с другими данными отклоняется. Файл получает серверный путь; локальные пути компьютера через API не принимаются. Запись события, очереди Telegram и полного текста выполняется в одной транзакции. Принятый файл может остаться на диске при прерывании до регистрации события; повтор использует те же байты. Автоматическая очистка таких файлов пока отсутствует.

## Очереди и восстановление

Входящий `update_id` и смещение Telegram записываются одной транзакцией. Поручение получает постоянный `clientUserMessageId` и неизменяемого адресата. Узел хранит поручение до первого отчёта компьютера. Компьютер сначала сохраняет его в SQLite; повтор выдачи не перезаписывает уже принятое поручение. Каждый переход состояния увеличивает ревизию отчёта. Подтверждение старой ревизии не убирает более новую из очереди, а старый отчёт не откатывает состояние на узле.

Цикл соединения с узлом работает отдельно от чтения Codex. Узел различает отсутствие компьютера и недоступность Codex при работающей службе. Отсутствие связи не переносит поручение на другую машину. Отзыв ключа блокирует последующие сетевые операции, но не отменяет уже полученные локальные поручения и не останавливает Codex удалённо.

Перед обращением к очереди Codex фиксируется `submitting`. После аварии оно становится `uncertain`. При потерянном подтверждении служба ищет `clientUserMessageId` в очереди и `userMessage.clientId` истории; отсутствие записи не доказывает отказ. Автоматический повтор такого поручения запрещён. Начало уже принятого поручения разрешено только в свободной задаче и первым элементом её очереди.

Между компьютером и узлом безопасен повтор события с тем же ключом. У Telegram нет соответствующего клиентского ключа. Поэтому потерянное подтверждение **Telegram** сохраняет состояние `uncertain` и требует проверки владельцем перед ручным повтором. Между принятием узлом и доставкой Telegram могут пройти время и перезапуск; это разные подтверждения.

Хранилище не ограничено по общему объёму и не удаляет историю автоматически. Резервная копия делается после остановки соответствующей службы. Для переноса узла необходим весь каталог состояния. Автоматического преобразования старых локальных привязок версии 1 в распределённые нет.

## Codex и вложения

При `codex.transport = unix` (также для старых настроек без transport) подключение — прямой WebSocket поверх Unix-сокета App Server: HTTP Upgrade выполняется библиотекой `ws`, каждое сообщение JSON-RPC передаётся отдельным текстовым кадром. Дочерний `app-server proxy` в рабочем режиме не запускается; построчный stdio-транспорт оставлен только для изолированных тестов протокола. Используются `thread/list`, `thread/read`, `thread/turns/list`, `thread/queue/add`, `thread/queue/list`, `thread/queue/start`. `thread/start`, `thread/fork` и `thread/resume` не вызываются. Отправка требует загруженной задачи и `canAcceptDirectInput: true`. Системные запросы разрешений положительно не подтверждаются.

Проект не перенастраивает настольный клиент и не задаёт его внутренние переменные окружения. `doctor` проверяет историю и очередь каждой явно выбранной задачи; при `all` — всех открытых задач с доступным вводом. Первый запуск `local` и `agent` выполняет ту же проверку до создания базы и получения поручений. Успех сохраняется в личном `codex-readiness.json` с контрольной суммой сокета, выбранных задач и привязки компьютера. Это допускает последующие запуски при временном отключении Codex; смена подключения требует новой проверки. `doctor` всегда выполняет свежую проверку. Отдельный демон с той же историей и успешная проверка протокола не доказывают связь с исходным окном: перед постоянной работой нужна ручная сквозная проверка.

Рабочий транспорт не запускает Codex CLI. Мастер и `launchd` не требуют пути к нему; старое поле `codex.executable` принимается, но не используется.

Текущая граница совместимости, проверенный инцидент с принудительной настройкой,
порядок восстановления и условия повторной проверки зафиксированы в
[codex-desktop-compatibility.md](codex-desktop-compatibility.md). Альтернатива, в
которой служба сама владеет App Server и задачами, считается другим продуктовым
режимом и не входит в эту архитектуру без отдельного согласования.

Чтение старого формата истории допускается только при `-32601` на `thread/turns/list`. Протокол очереди экспериментальный и требует проверки при обновлениях Codex. История опрашивается; длинные истории обходятся полностью. Оптимизация этого обхода остаётся отдельной работой.

Файлы создаёт Codex и явно перечисляет в `manifest.json` конкретного поручения. Компьютер проверяет пути, ссылки, сигнатуру, размер и SHA-256; перед передачей перечитывает файл. Узел повторно проверяет размер, формат, сумму и принадлежность поручения. Перед Telegram файл снова проверяется. Визуальное качество и содержательная верность этим не доказываются.

## Подключение Desktop

`DesktopAdapter` реализует тот же `CodexPort` для local и agent. Coordinator,
CodexWorker, межкомпьютерный протокол и проверка вложений сохраняются.
`DesktopCatalog` при каждом опросе обновляет список основных задач по session_meta,
исключает служебные источники и неоднозначные идентификаторы. `RolloutReader` извлекает
название из первой строки первого пользовательского запроса и хранит курсор
законченных строк в памяти; после перезапуска перечитывает историю, а постоянные
ключи Store предотвращают повторную доставку.

`DesktopMailbox` хранит отдельную SQLite-очередь, привязанную к компьютеру,
каталогу журналов и Telegram/единому узлу. Выдача атомарно меняет ready на claimed
и создаёт ключ подтверждения. MCP не имеет доступа к секретам Telegram и не
вызывает приложение самостоятельно: это делает задача-диспетчер встроенным
инструментом send_message_to_thread. Единственная попытка подтверждается как
accepted либо uncertain. Claimed/uncertain не выдаются повторно. Входная метка
в событии исходного хода позволяет восстановить принятие без доверия к ответу
модели о завершении. Итог берётся из task_complete, затем работает прежняя
доставка сводки и файлов. Неопределённое поручение блокирует только свою задачу.

Desktop не требует socketPath; сохранённое поле используется только unix.
Пустой threadIds означает автоматический выбор, непустой ограничивает набор.
MCP desktop_register сохраняет идентификатор диспетчера в desktop.sqlite;
desktop_claim повторно регистрирует своего вызывающего диспетчера перед выдачей.
Эти идентификаторы исключаются при наблюдении, приёме поручения и передаче
ожидающих уведомлений (как local, так и agent). Список исключений перечитывается
из общей базы без перезапуска; сам плагин берёт свой ID из CODEX_THREAD_ID.
Автоматический режим до первой регистрации диспетчера не начинает наблюдение.
После регистрации пустой каталог допускает ожидание будущих задач.
Doctor проверяет доступность журналов и
локальной очереди, а способность диспетчера отправлять проверяется отдельным
ручным опытом. Формат журналов не является стабильным внешним API; состояние
приложения повторно проверяется диспетчером. Атомарной операции «проверить
занятость и отправить» у используемого инструмента нет.

Плагин подготавливается на каждом компьютере командой desktop prepare:
поставляемый навык копируется в личный каталог, .mcp.json генерируется с
абсолютными путями к Node.js и проекту. После переноса нужна повторная подготовка.
Установка в приложение и расписание остаются явными шагами.
Схема, ограничения и восстановление: [desktop-mode.md](desktop-mode.md).

Автоматическое обнаружение не меняет ключ маршрута hostId + threadId и не
создаёт новые задачи Codex. Состояние enabledAt сохраняет время первого включения
с точностью до миллисекунд; timestamp завершения Desktop отделяет старые итоги
от новых, в том числе в пределах одной секунды.
