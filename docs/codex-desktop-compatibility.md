# Совместимость с настольным Codex

## Текущее решение

На 14 сентября 2026 года сквозная связь с открытой задачей текущего настольного
Codex **не подтверждена**. Службу Codex Telegram запускать и устанавливать для
автозапуска нельзя, пока `doctor` не увидит через один и тот же App Server:

1. открытую исходную задачу настольного приложения;
2. её историю;
3. доступную очередь и `canAcceptDirectInput: true`.

Отдельный App Server, который видит ту же сохранённую историю или те же
идентификаторы, не выполняет это условие. Он не владеет открытой задачей и не
доказывает, что ответ появится в том же окне приложения.

Для проверенных версий не найден документированный способ заставить настольное
приложение и внешнюю службу использовать один App Server. Это ограничение
текущей интеграции, а не ошибка токена Telegram, сети или локального адреса.

## Требование продукта

Codex Telegram должен продолжать именно исходную задачу владельца. Поэтому
проект:

- не создаёт, не копирует, не возобновляет и не разветвляет задачу для обхода
  недоступного общего сервера;
- не считает совпадение истории или идентификатора доказательством связи;
- не перенастраивает настольное приложение и не расширяет его разрешения;
- не запускает отдельный App Server вместо сервера исходной задачи;
- допускает запуск только после успешного `doctor` и ручной проверки ответа в
  том же окне.

## Основание протокола

Согласно [документации Codex App Server](https://learn.chatgpt.com/docs/app-server),
Unix-сокет использует WebSocket со стандартным HTTP Upgrade, а каждое сообщение
JSON-RPC передаётся отдельным текстовым кадром. После `initialize` клиент
отправляет уведомление `initialized`.

Документация обозначает WebSocket-транспорт App Server как экспериментальный и
неподдерживаемый для произвольных интеграций. Методы очереди, полученные из схем
проверенной версии Codex, также требуют повторной сверки при обновлении.
Официальная документация не описывает внутренние переменные настольного клиента
как способ подключить его открытую задачу к внешнему демону.

Поэтому проект использует прямой WebSocket поверх Unix-сокета, но не обещает
совместимость с любой версией настольного приложения только по факту наличия
сокета.

## Что проверено 14 сентября 2026 года

Среда:

- macOS;
- Node.js 24.18.0;
- CLI из настольного приложения 0.154.0-alpha.6.2;
- управляемый отдельный CLI и App Server 0.154.0.

Последовательность проверки:

1. Первоначальный `doctor` сообщил об отсутствии общего сокета.
2. Управляемый отдельный Codex был установлен и его демон запущен на Unix-сокете.
3. Передача построчного JSON через `app-server proxy` завершалась ожиданием
   `initialize`. Проверка настоящего HTTP Upgrade показала, что сокет ожидает
   WebSocket, а не необрамлённый поток JSON.
4. Рабочий транспорт проекта заменён на прямой WebSocket. Изолированный
   построчный транспорт сохранён только для тестов.
5. После исправления отдельный сервер успешно выполнил `initialize`, чтение
   списка задач и истории. `doctor` при этом не нашёл открытую задачу,
   обслуживаемую этим сервером: настольное приложение продолжало работать со
   своим встроенным процессом через stdio.
6. Краткий пробный запуск подтвердил запуск Telegram-получателя, создание
   локальной базы и два цикла без диагностических ошибок. Очередь была пустой;
   это не сквозная проверка и не доказательство связи с Codex.
7. Затем была отвергнутая попытка направить настольный клиент на отдельный сокет
   с помощью внутренних переменных окружения. После перезапуска владелец увидел
   ошибку подключения к `127.0.0.0`; для восстановления потребовалась
   перезагрузка компьютера. Точный источник этого адреса в сохранённом журнале
   не установлен, но сбой последовал непосредственно за принудительной
   настройкой, поэтому этот путь признан небезопасным.
8. Внутренние переменные удалены. После перезагрузки настольное приложение снова
   запускается штатно со встроенным stdio-сервером; отдельный демон и его сокет
   не работают.
9. Локальная SQLite-база, созданная во время пробного запуска против неверного
   сервера, вместе с WAL-файлами перенесена в восстановимый карантин вне Git.
   Telegram-служба не оставлена запущенной.

Автоматическая проверка после изменений: `npm run check`, 41 из 41 проверок.
Она подтверждает реализацию транспорта и защитных условий, но не заменяет
проверку с настоящим окном Codex.

## Разбор причины

Были две независимые проблемы:

1. **Несовпадение транспорта.** Проект отправлял построчный JSON в сокет,
   ожидающий WebSocket. Эта ошибка исправлена и покрыта тестом HTTP Upgrade,
   текстовых кадров и уведомления `initialized`.
2. **Несовпадение владельца задачи.** Управляемый демон и встроенный сервер
   настольного приложения являются разными процессами. Первый может читать общую
   историю на диске, но не становится владельцем уже открытой задачи второго.
   Эта проблема не решается исправлением транспорта.

Второй пункт остаётся блокирующим. Адрес в интернете, туннель или другой путь к
тому же отдельному демону его не устраняют.

## Запрещённые обходы

До появления поддерживаемого способа подключения нельзя:

- задавать внутренние `CODEX_APP_SERVER_WS_URL` или
  `CODEX_APP_SERVER_USE_LOCAL_DAEMON` для настольного приложения;
- добавлять эти переменные в профиль оболочки, пользовательскую службу или
  постоянные настройки запуска;
- считать отдельно запущенный демон общим только потому, что он читает ту же
  историю;
- создавать, возобновлять или разветвлять другую задачу вместо исходной;
- запускать `npm start` или устанавливать службу после неуспешного `doctor`;
- отмечать сквозную приёмку по имитаторам, чтению истории или отсутствию ошибок
  в нескольких циклах опроса.

## Восстановление после неудачной принудительной настройки

На macOS сначала удалить переменные из окружения пользовательского сеанса:

```sh
launchctl unsetenv CODEX_APP_SERVER_WS_URL
launchctl unsetenv CODEX_APP_SERVER_USE_LOCAL_DAEMON
```

Затем полностью завершить настольное приложение и открыть его снова. Если оно
по-прежнему не запускается, выйти из пользовательского сеанса или перезагрузить
компьютер: это очищает унаследованное окружение сеанса. После восстановления не
возвращать эти переменные в профиль оболочки или файл службы.

Если управляемый отдельный демон был запущен намеренно, его следует остановить
тем же установленным CLI командой `codex app-server daemon stop`. Нельзя
завершать процессы по широкому шаблону: настольное приложение использует свой
дочерний App Server.

Состояние Codex Telegram, созданное во время проверки против неверного сервера,
нужно при остановленной службе перенести в отдельный восстановимый карантин, а
не смешивать с будущей рабочей базой. Токены, настройки, базы, WAL-файлы и
журналы не добавляются в Git и не публикуются в диагностике.

## Условия повторной проверки

Повторять интеграцию следует только после обновления Codex или появления
документированного способа подключить внешний клиент к серверу открытой задачи.
Порядок проверки:

1. Записать версии приложения, CLI, App Server, Node.js и ОС без личных путей и
   идентификаторов.
2. Убедиться, что внутренние переменные не заданы и приложение штатно
   перезапускается.
3. Получить адрес общего сервера из официальной документации или поддерживаемой
   настройки приложения, а не из скрытой переменной.
4. Открыть в приложении две безопасные тестовые задачи.
5. Запустить `doctor`. Он должен увидеть обе открытые задачи, их историю и
   очереди на одном сервере.
6. Запустить программу вручную и отправить из Telegram безвредный контрольный
   текст в каждую задачу.
7. Убедиться, что каждый текст появился в соответствующем исходном окне без
   создания другой задачи.
8. Полностью перезапустить приложение и компьютер, затем повторить `doctor` и
   один контрольный ответ.
9. Только после этого выполнять оставшуюся сквозную проверку и проверять
   `service install`.

При любом неопределённом результате запуск останавливается. Отсутствие записи в
очереди после потерянного подтверждения не разрешает автоматический повтор.

## Возможные дальнейшие направления

1. **Сохранить текущий продуктовый контракт.** Дождаться поддерживаемого общего
   App Server или официального интерфейса настольного приложения. Это выбранный
   вариант: ответы должны попадать в существующую задачу.
2. **Передать владение задачами службе.** Служба может запускать свой App Server
   и свои задачи, но они не будут исходными задачами открытого настольного
   клиента. Это другое поведение и требует отдельного решения, архитектурной
   записи и явного согласования; текущая реализация так не делает.

## Состояние после восстановления

- настольное приложение запускается штатно;
- внутренние переменные пользовательского сеанса удалены;
- отдельный управляемый демон не запущен;
- Codex Telegram не оставлен работающим и не установлен как служба;
- пробная база изолирована вне Git;
- транспорт WebSocket исправлен и проверен автоматически;
- сквозная совместимость остаётся заблокированной до появления поддерживаемого
  общего сервера.
