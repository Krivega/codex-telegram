Node.js 25.2.1. Команда `npm run check`: проверка типов и 62 теста проходят (включая новый Desktop).
Настоящие Codex и Telegram в автоматических сценариях заменены имитаторами.
Исторические результаты коммита с 41 тестом, CLI 0.154.0-alpha.6.2 и отдельным
App Server 0.154.0 сохранены в [разборе совместимости](codex-desktop-compatibility.md).

- Проверка типов TypeScript.
- Маршрутизация ответов между двумя задачами без смешивания.
- Защита от посторонних отправителей и неизвестных сообщений.
- Защита от повторного входящего обновления.
- Восстановление входящих, привязок и неопределённых операций после открытия базы заново.
- Сверка неопределённого поручения с очередью Codex без повторной отправки.
- Доставка зарегистрированного документа и привязка ответа на документ.
- Проверка путей, ссылок, размера и сигнатуры вложений.
- Разделение длинного текста с Unicode без повреждения символов.
- Протокол инициализации, чтения и очереди через отдельный построчный тестовый процесс; HTTP Upgrade, текстовые кадры и уведомление `initialized` через тестовый Unix-сокет WebSocket.
- Форматы запросов Bot API, обработка ограничения частоты и потери ответа без раскрытия токена.
- Раздельное хранение секрета и настроек, блокировка второй копии.
- Настройки без Codex CLI и совместимость со старым `codex.executable`. Поиск CLI удалён из мастера, путь к нему не требуется для автозапуска.
- Первый запуск `local` после отказа `doctor` не получает сообщения и не создаёт базу. Существующая база без результата проверки не обходит это условие и сохраняет своё состояние.
- Первый запуск `agent` после отказа проверки не создаёт базу и не обращается к единому узлу. Результат одного подключения не действует для другого компьютера или узла.
- История и очередь проверяются для обеих выбранных задач; отсутствующая, закрытая задача или отказ её очереди вызывают ошибку. При `all` сохранённая закрытая история не мешает проверке открытых задач.
- Успешная проверка сохраняется с правами 600 без личных путей и содержимого задач. После отключения Codex повторный запуск сохраняет поручение и смещение Telegram; изменение настроек или повреждённый результат требуют новой проверки. `doctor` всегда проверяет текущее состояние.
- Структура файла автоматического запуска macOS проверена через `plutil -lint`; сама служба не устанавливалась.

По отчёту автора коммита 7bc48a66 на другом компьютере выполнялся ручной пробный `npm start` с личными настройками: Telegram-получатель запустился, локальная база создалась, очередь осталась пустой, за два цикла опроса диагностических ошибок не появилось. Служба затем остановлена через `Ctrl+C`; это не проверка `launchd` и не двусторонняя проверка с окном Codex. В ходе исправлений этот запуск с настоящим ботом не повторялся.

Транспортные тесты используют имитаторы. PDF в тесте — образец байтов для проверки передачи, не визуально проверенный отчёт.

## Автоматическое обнаружение задач Desktop

Добавлены проверки появления задачи после запуска с пустым каталогом, продолжения
старой задачи, отсутствия рассылки старых итогов в пределах одной секунды,
сохранения маршрута ответа и отсутствия повторных итогов после перезапуска.
Проверены служебные источники, подзадачи, архивирование, неполный заголовок,
повреждённый журнал, ссылки, дубликаты и ручное ограничение набора задач.
Регистрация диспетчера действует между двумя работающими подключениями и
блокирует ожидающие уведомления как локально, так и перед отправкой единому узлу.
Отдельная проверка подтверждает, что `/tasks` показывает первую строку первого
пользовательского запроса вместо UUID и сохраняет адрес исходной задачи.

На доступных локальных журналах отдельно проверено чтение только метаданных:
распознаны 38 основных задач; обнаружены источники служебных подзадач с parent_thread_id
и source.subagent. Это не новая сквозная проверка Telegram или установленного плагина.
Формат MCP изменился: desktop_claim требует dispatcherThreadId; для первого
подключения добавлен desktop_register. Обновлённый плагин нужно переустановить.

## Дополнительно проверено для одного бота и двух компьютеров

Сетевые сценарии используют настоящий HTTP-сервер на локальном порту, отдельную базу узла и две независимые базы компьютеров. Внешние Codex и Telegram заменены имитаторами. Это проверяет протокол между службами, но не физическую сеть и не настольное приложение.

- Совпадающие идентификаторы задач и выполнений на двух компьютерах не смешиваются.
- Поручение отключённому компьютеру сохраняется; другой компьютер его не получает.
- Перезапуск узла и компьютера сохраняет адресата и не повторяет принятый запрос.
- Потеря ответа после записи события или отчёта на узле не создаёт дубликат.
- Устаревшая ревизия отчёта не откатывает состояние поручения.
- Неопределённый запрос Codex после перезапуска сверяется с его очередью.
- PDF и PNG проходят через узел с сохранением байтов и адреса ответа на файл.
- Узел отклоняет чужое вложение, неправильную сумму и формат, превышение размера и числа файлов, подмену повторного события.
- `/full` читает сохранённый итог при отключённом компьютере, `/tasks` сохраняет адреса, `/feedback` сохраняет замечание.
- Код истекает, повтор допускается только с прежним ключом, отзыв блокирует доступ и повторную привязку старым кодом.
- Ключ одного компьютера не позволяет подтвердить поручение другого.
- Прямой удалённый HTTP и адреса с секретами отклоняются; перенаправление не передаёт ключ другому HTTP-серверу.
- Смена адреса при прежней идентичности узла разрешена; чужой `hubId` отклоняется.
- Команды `pair`, `hosts`, `status`, `config`, `revoke` проверены в отдельных процессах без обращения к настоящему боту; вывод состояния не содержит секретов.

## Не подтверждено

- Доступ к исходной задаче через unix; для Desktop подтверждён описанный выше опыт.
- Уведомление в настоящий Telegram и ответ обратно в окно Codex.
- Создание настоящего снимка и PDF после поручения из Telegram.
- Сохранение инструментов настольного приложения при внешнем запуске очереди.
- Реальный запуск `launchd`, восстановление после сна и перезагрузки Mac.
- Работа на Linux и Windows.
- Развёртывание HTTPS с настоящим доменом, доверенным сертификатом или обратным прокси.
- Пошаговая настройка с настоящим токеном и кодом на двух физических компьютерах.
- Практический перенос узла, резервной копии и задач Codex на другую машину.

Управляемый App Server 0.154.0 временно запускался на стандартном сокете `~/.codex/app-server-control/app-server-control.sock`. Прямое WebSocket-подключение прошло `initialize`, `thread/list` и чтение истории, но сервер не обслуживал открытую задачу настольного приложения. Попытка принудительно направить приложение на этот сокет через внутренние переменные привела при перезапуске к ошибке подключения к `127.0.0.0`, которую владелец смог снять только перезагрузкой компьютера. Переменные удалены, отдельный демон после перезагрузки не запущен, приложение снова использует штатный встроенный сервер. Созданная при пробном запуске SQLite-база вместе с WAL-файлами перенесена в восстановимый карантин и не будет использоваться при следующем запуске. Этот способ отвергнут и не считается частичной приёмкой. Полный разбор, восстановление и безопасный порядок повторной проверки находятся в [codex-desktop-compatibility.md](codex-desktop-compatibility.md).

## Сквозная проверка на компьютере владельца

Для Desktop сначала выполните [настройку плагина и диспетчера](desktop-mode.md);
при ответах из Telegram запускайте проход диспетчера либо проверенное расписание.

1. Открыть в Codex две небольшие проверочные задачи. Настроить отдельного бота через `npm run setup`, Для Desktop выбрать `all` и зарегистрировать диспетчер; при ограниченном опыте можно указать оба идентификатора в `codex.threadIds`. Пройти `npm run doctor`.
2. Запустить программу вручную через `npm start`. Выполнить безопасное текстовое поручение в каждой из этих задач.
3. Убедиться, что пришли два уведомления с правильными названиями; в Desktop это первая строка первого пользовательского запроса. Ответить на каждое разным контрольным текстом. Проверить, что сообщение появилось в соответствующем окне исходной задачи, без создания другой задачи.
4. Попросить снимок тестовой страницы. Открыть полученный документ и сверить его с результатом в Codex.
5. Попросить PDF с коротким отчётом. Открыть файл, проверить текст и оформление. Ответить на сам документ и проверить адресата.
6. Во время выполнения отправить ещё одно поручение: убедиться, что текущая работа не прервана и порядок очереди сохранён.
7. Остановить службу между получением и обработкой, затем запустить. Проверить отсутствие повторного поручения.
8. Прервать сеть во время отправки. Если подтверждение потеряно, состояние должно быть неопределённым. Проверить Telegram перед ручным повтором.
9. Проверить ожидание системного разрешения: служба не подтверждает его автоматически, задача остаётся под управлением владельца.
10. После успешного ручного запуска проверить `service install`, вход в систему и остановку через `service uninstall`.

Критерий готовности двусторонней связи — видимый ответ в той же задаче настольного приложения. Совпадение истории или идентификатора при запуске второго независимого сервера недостаточно.

## Сквозная проверка общего бота

1. Остановить все прежние службы, читающие этого бота. Настроить и запустить роль `hub` в отдельном каталоге.
2. Выдать два отдельных кода. Настроить роли `agent` на двух физических компьютерах, например «MacBook» и «Mac mini». Пройти `doctor` на всех трёх установках.
3. Выполнить задачу на каждом компьютере. Проверить две подписи в одной переписке Telegram.
4. Ответить на каждое уведомление разным контрольным текстом. Увидеть тексты в соответствующих исходных задачах Codex.
5. Выключить одну локальную службу, подождать минуту, проверить `/hosts` и ответить на её старое уведомление. Второй компьютер не должен получить поручение. После запуска первой службы поручение выполняется ровно один раз.
6. Попросить PDF на одном компьютере и снимок страницы на другом. Открыть файлы, проверить содержание и ответить на каждый. Адреса должны сохраниться.
7. Перезапустить единый узел. Ответить на уведомление, полученное до перезапуска; проверить тот же адрес.
8. Отключить компьютер и запросить `/full` для его завершённой задачи. Итог должен читаться с узла.
9. Отозвать ключ одного компьютера. Его `doctor` должен показать отказ; новые ответы на старые уведомления не принимаются. У второго компьютера связь сохраняется.
10. После успешной проверки установить службы и проверить вход в систему, сон и восстановление сети. Записать версии Codex, адрес общего сервера, проверенные ОС и успешные сценарии.

Ни один из этих ручных пунктов не отмечается выполненным по результатам автоматических тестов.
